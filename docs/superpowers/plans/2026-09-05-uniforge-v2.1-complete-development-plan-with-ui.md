# UniForge V2.1 完整开发计划（含 Stage 0.5 UI / UX 设计阶段）

> **For agentic workers:** REQUIRED SUB-SKILL: 使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 按任务逐项执行。进入实际编码前应在独立 Git worktree 中工作；每个任务必须经过测试、实现、验证、审查和提交。

**Goal:** 按《UniForge 产品与架构设计规格 V2.1》分阶段实现一个 Windows 优先、本地优先、拥有自主领域内核、Agent Runtime 可替换、数据可追踪、权限可审批、状态可恢复的大学生 AI 桌面工作台。

**Architecture:** UniForge 自己拥有 Domain Core、Application Services、SQLite 真源、Event Store、Permission/Approval、Model Gateway、Tool Gateway、Knowledge/Memory 与各产品领域。LangGraph、Bok、MCP、OCR、语音、文档解析等第三方能力仅通过稳定契约接入。应用内 Agent 的持久软件开发仅限项目实践中的授权软件项目工作副本；课程仅允许授权临时沙箱执行和输出，但绝不能修改 UniForge 本体源码、安装目录、更新器或核心迁移逻辑。

**Tech Stack:** Electron、React、TypeScript、Node.js、SQLite、Electron Forge、Monaco、Vitest、React Testing Library、Playwright；LangGraph.js 作为复杂 Agent Runtime 首选适配器；MCP 作为外部工具标准协议；`ts-fsrs` 作为基础间隔重复实现；OCR、语音、复杂文档解析、Sandbox 采用独立 Sidecar / 受控进程。

**Spec:** `docs/specs/2026-09-05-uniforge-product-architecture-spec-v2.1-no-dev-zone.md`

# 1. 计划性质与使用规则

本文是 UniForge V2.1 的 **Master Development Plan**。

它解决两个问题：

1. 整体上，UniForge 应该按照什么顺序建设；
2. 每个阶段需要完成哪些真实能力、测试、证据和 Git 检查点。

它不代表可以一次性并行开发所有模块。

按照上位规格，开发必须严格采用：

```text

↓

↓

```

每一个阶段都必须独立通过退出门槛后，才能正式进入下一阶段。

# 2. V2.1 的硬性边界

## 2.1 UniForge 本体不允许应用内自我开发

取消以下能力：

- `07 开发区`
- 应用内部修改 UniForge 本体源码
- Agent 修改 UniForge 安装目录
- Agent 修改 UniForge 更新器
- Agent 修改核心数据库迁移代码
- Agent 修改权限内核
- Agent 在运行中的产品内部构建并替换自身

```text
↓

```

产品内部仅允许安装经过验证的正式更新。

# 3. 全局设计约束

整个开发周期持续遵守：

1. UniForge 是平台，不是某个 Agent Framework 的 UI。
2. 业务对象归 Domain Core。
3. Agent 不得直接拥有业务数据库。
4. 一个对象只有一个正式真源。
5. Agent Runtime 必须可替换。
6. 模型供应商必须可替换。
7. Tool、Connector、Sidecar 必须可替换。
8. MCP 不用于内部 Domain Service 通信。
9. LangGraph Checkpoint 不是 Domain State。
10. Obsidian 正式笔记的真源是 Markdown。
11. Git 项目的版本真源是 Git。
12. Personal Memory 与 Conversation Context 分离。
13. 向量索引、全文索引和派生 Projection 都必须可以重建。
14. 高风险动作必须审批。
15. 复杂 Agent 运行必须可暂停、恢复、取消、回放。
16. 所有重要写入必须留下证据。
17. 失败必须真实呈现，不允许用 Mock 或假成功掩盖失败。
18. API Key、登录凭据、Cookie、Git 凭据不得进入普通日志、普通数据库、备份和 Git。
19. Renderer 不直接访问 Node、SQLite、文件系统、系统凭据和 shell。
20. 应用内任何 Agent 都不能获得 UniForge 本体写权限。

## 6.2 每个任务的标准执行循环

所有实现任务统一执行：

```text
1. 写失败测试
2. 确认测试按预期失败
3. 实现最小代码
4. 运行目标测试
5. 运行相关回归测试
6. 静态检查 / 类型检查
7. 自我审查
8. 提交 Git
```

---

## 6.3 禁止行为

禁止：

- 一个提交塞入多个无关领域；
- 测试失败时宣称功能完成；
- 删除失败测试来“修复”构建；
- 弱化断言来通过验收；
- 修改验收标准来配合已有实现；
- 用 Mock 结果冒充真实外部调用成功；
- 为了方便 Agent 而放宽 Renderer 权限；
- 将 API Key 保存到普通配置文件；
- 为项目 Agent 暴露 UniForge 本体目录。

# 10.20 阶段 0.5：UI / UX Design & Design System

## 10.20.1 阶段定位

阶段 0.5 是 **设计冻结阶段**，不是业务编码阶段。

目标不是提前实现 Stage 1～5 的所有 React 页面，而是：

> 在 Stage 0 架构、IPC、Domain Contract、Agent Runtime、权限边界和 Workspace 规则稳定后，统一确定整个 UniForge 的视觉语言、信息架构、页面框架、关键交互和跨模块组件，使后续各阶段开发不再“边写代码边决定产品长什么样”。

推荐顺序：

```text
Stage 0 Architecture Foundation
        ↓
Stage 0 Acceptance
        ↓
Stage 0.5 UI / UX Design
        ↓
Design System V1
        ↓
Core Prototype Approval
        ↓
Stage 1 Detailed Implementation Plan
        ↓
Stage 1 React / Electron Implementation
```

如果 Stage 0 的核心 Contract 尚未稳定，不应开始完整 UI 设计。

---

## 10.20.2 硬性原则

1. 先设计，再实现。
2. 可以设计 Stage 1～5 的完整视觉和导航，但不得提前编码 Stage 2～5 的业务逻辑。
3. UI 必须服从真实 Domain 和 Permission 模型。
4. 不允许用“假 AI 状态”“假审批”“假同步”作为正式交互逻辑。
5. 后续业务阶段允许微调局部页面，但必须复用 Design System V1。
6. 跨模块视觉模式进入共享 Design System，不允许各模块重复造轮子。
7. Desktop-first，优先 Windows 桌面密度与多面板体验。
8. AI 应表现为系统能力，而不是把每个页面都做成聊天框。
9. 页面以对象、任务和上下文为中心。
10. Agent 的运行、暂停、审批、失败、恢复和成本必须可理解。

## 15.11 Task 5.10：Self-Modification Guard

这是 V2.1 的关键安全验收。

必须建立：

```text

```

至少阻止：

- current UniForge installation
- update binaries
- core migration resources
- detected UniForge source repository
- credential storage
- unrelated workspaces

即便用户项目通过 symlink / junction 指向这些位置，也必须拒绝。

```text
↓

↓
```

不是弹出“确认后继续修改 UniForge”。

# 22. 失败策略

## Model Failure

```text
retry policy
→ fallback if allowed
→ pause if no valid model
```

不能伪造回答。

## Tool Failure

记录真实 error，允许 retry/cancel。

## Sidecar Failure

重启或降级，不拖垮主程序。

## Connector Failure

停止该来源，不影响其他模块。

## Migration Failure

阻止继续写入，恢复备份或执行经过验证的 forward fix。

## Agent Failure

保留 Event、Checkpoint、已产生 Artifact，并明确标记 incomplete。

## Project Build Failure

保留失败证据，不标记完成。

# 25. 风险清单

## R1：Agent Framework 锁定

**控制：**
所有业务只依赖 `AgentRuntime` Contract。

## R2：本地数据损坏

**控制：**
Migration、Transaction、Backup、Restore、Recycle Bin。

## R3：Agent 越权文件访问

**控制：**
Workspace Scope + canonical path + junction/symlink 防护 + Approval。

## R4：模型上传敏感数据

**控制：**
Model Gateway 数据范围提示 + Provider 切换确认。

## R5：Connector 平台变化

**控制：**
独立 Connector Host，可关闭、可卸载、不成为核心启动依赖。

## R6：英语题库版权

**控制：**
Schema 与内容分离；未核验内容不打包。

## R7：Memory 错误长期化

**控制：**
Conversation → Candidate → Evidence → Authorization → Claim。

## R8：新闻误报

**控制：**
Source Role + Verification + Correction Timeline。

## R9：软件项目 Agent 误伤 UniForge

**控制：**
V2.1 ProtectedPathPolicy，禁止任何“确认后解除”路径。

## R10：过度工程化

**控制：**
简单 AI 走 Native Runtime；复杂任务才走 LangGraph。

# 30. 最终开发原则

UniForge 的开发顺序应始终围绕：

```text
先建立可靠内核
↓
再冻结 UI / UX 与 Design System
↓
再完成一个真实课程闭环
↓
再扩展英语
↓
再建立知识与情报
↓
再复用知识底座建设 AI 新闻
↓
最后建设复杂项目实践与软件项目能力
```

而不是：

```text
先把所有导航和页面做出来
↓
再慢慢补后端
```

V2.1 的最终底线：

> **UniForge 可以帮助用户开发自己的软件，但 UniForge 不能在运行中的产品内部开发和改写自己。**

这样可以同时保留 AI 工作台的强能力，又避免自我修改稳定内核带来的不可控故障风险。
